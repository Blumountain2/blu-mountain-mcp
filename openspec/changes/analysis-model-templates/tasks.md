## 3. Tenant onboarding profile (buildable now)

- [x] 3.1 Build the profile-production step: one tenant's field-profiling result (plus that tenant's known vertical's default-trust guidance, when known) → one tenant-specific onboarding profile record — a lightweight runtime parameter, not a copy of the framework/skill/prompt (corrected from the first draft's "instantiated copy" design). `gateway/frameworks/onboarding.py::produce_onboarding_profile`, backed by `gateway/schema.sql::tenant_onboarding_profiles`/`tenant_onboarding_profile_fields` (append-only per profile, never mutated except the field-level `status` transition in 3.3). Only populated fields become candidates; a field is `confirmed_relevant` (carrying the framework's guidance) if the tenant's known vertical already discusses it (`trust_by_default` or `unreliable_by_default` — either counts as the framework actively addressing the field, not silence about it), else `needs_review`.
- [x] 3.2 Name the onboarding profile using the tenant's effective display name (`portal_name` → `hub_domain` → `hub_id`, reusing the existing resolution already built for the live session). `gateway/frameworks/onboarding.py::_effective_tenant_name`, matching `session/live_session.py`'s COALESCE pattern exactly; the name is captured as a snapshot at production time (`tenant_onboarding_profiles.name`), not a live join, so a later tenant rename never silently alters an already-produced profile — consistent with `analysis_content`'s own versioned-snapshot philosophy. Tested (`test_profile_is_named_after_portal_name_when_present`, `test_profile_name_falls_back_to_hub_domain_then_hub_id`) and confirmed live 2026-08-25 (see 3.5): `148997330` → "Blu Mountain & Gumpper", `149094230` → "Blu Mountain - Test Account".
- [x] 3.3 Implement the human-review checkpoint: any profiled field the tenant's framework guidance doesn't address is marked for review, and the profile is flagged not-final until every such field is reviewed. `gateway/frameworks/onboarding.py::review_field` (transitions `needs_review` → `confirmed_relevant`/`confirmed_irrelevant`, records `reviewed_by`/`reviewed_at`) and `OnboardingProfile.is_final` (`True` only once no field remains `needs_review`). Tested: auto-confirm vs needs-review assignment, unpopulated-field exclusion, `is_final` before/after review, and rejection (`confirmed_irrelevant`) — `gateway/tests/frameworks/test_onboarding.py`.
- [x] 3.4 Write isolation tests proving an onboarding profile can only ever be associated with the one tenant it was produced for, and that producing one for tenant B never reads tenant A's data or profile. Structural, not just conventional: `get_profile_for_tenant` and `review_field` both enforce `hub_id` directly in the query (a JOIN/WHERE, not a Python-level check a caller could skip) — a wrong `hub_id` returns `None`/`False` indistinguishably from "doesn't exist," so it can't be used to probe another tenant's profile. Tested: `test_get_profile_for_tenant_returns_none_for_the_wrong_tenant`, `test_review_field_cannot_target_another_tenants_profile`, `test_two_tenants_produce_distinctly_scoped_profiles`, and `test_produce_onboarding_profile_only_ever_constructs_client_for_the_requested_tenant` (proves isolation at the HubSpot-pull layer too, not just storage) — `gateway/tests/frameworks/test_onboarding.py`. Full suite: 218 tests passing.
- [x] 3.5 Run the full pipeline end to end against both real test portals, confirming two distinctly-named, tenant-scoped onboarding profiles come out the other end. **Confirmed live 2026-08-25**: ran `produce_onboarding_profile` for `CONTACT`/`COMPANY`/`DEAL` against both real portals inside the recreated running container. `148997330` → profile named "Blu Mountain & Gumpper", 8 populated fields; `149094230` → profile named "Blu Mountain - Test Account", 14 populated fields — the differing field counts are themselves live confirmation that per-tenant field variation is real, not assumed.
