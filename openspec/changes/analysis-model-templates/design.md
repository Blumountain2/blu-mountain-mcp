## Context

This project (`blu-mountain-mcp`) currently ends at the boundary `HubSpot_MCP_Server_Spec_v1.2.md` drew on purpose: it pulls read-only HubSpot data, normalizes it, and stages it into Airtable per client, and separately lets staff query a tenant's HubSpot data live through Claude via an MCP session. The spec's own Section 1.2 names "the analysis jobs and dashboards that read from the Airtable staging layer" as explicitly out of scope. This change is the first step into that previously out-of-scope territory.

The documentation this plan was originally blocked on has since been delivered (`context/Blu Mountain Documentation/`, gitignored real client data, converted from the client's original `.docx`/`.xlsx` files and verified word-for-word complete before the originals were removed). It describes a materially different mechanism than this design first assumed, and resolves some open questions from the first draft while leaving others genuinely open — Blu Mountain's own documentation admits as much in its own "Notes on Future Refinement" section.

Confirmed, unchanged from the first draft: "AI model" means a Claude prompt/agent configuration — a system prompt plus an analysis workflow — not a trained or fine-tuned machine learning model. Nothing in the delivered documentation contradicts this; it describes Claude skills and prompts throughout, never an ML training or evaluation pipeline.

## Goals / Non-Goals

**Goals:**
- Store and serve the six vertical frameworks, the operational skill (`account-diagnostic-SKILL`), and the runtime prompt (`Weekly_Diagnostic_Prompt`) Blu Mountain already authored, versioned and independent of any one tenant.
- Discover, per tenant, which of that tenant's real HubSpot fields are actually populated and in active use — reusing the existing pull layer, informed by each framework's own stated default-trust/default-unreliable property guidance.
- Produce, per tenant, a named onboarding profile suitable as a runtime parameter alongside a shared vertical framework — not a persisted, forked copy of the framework or skill.
- Make explicit, and enforce by test, that this layer reads only raw HubSpot object data already reachable through the existing pull mechanism.
- **(Added 2026-08-28)** Build one HubSpot data-*gathering* agent per vertical — an AI agent, in the Claude-API-tool-use sense (no training involved), that dynamically decides which of the existing allowlisted pull methods to call and with what parameters, informed by that vertical's framework. It gathers data; it does not interpret or diagnose it — see Non-Goals and the Non-Negotiables below for the line this draws.

**Non-Goals:**
- Authoring vertical-framework content. Already done, by Blu Mountain, delivered as real documentation — not this project's to write.
- Any machine-learning training, fine-tuning, evaluation-dataset curation, or model hosting.
- Pulling HubSpot's own workflows, reports, or any other endpoint that returns HubSpot-derived analysis rather than raw object data.
- Building the three downstream analysis jobs (Funnel, Maintenance, KPIs) that would actually run a framework against a tenant's staged data and onboarding profile. Their shape is now known (see Decisions below), but this project does not treat building them as scheduled future work. They stay out of scope until the original spec's boundary (`HubSpot_MCP_Server_Spec_v1.2.md` Section 1.2) is explicitly revisited — reconfirmed 2026-08-27, and again 2026-08-28 specifically regarding the new pull-agent goal above (see Decisions: "gathering, not analysis").
- Any interpretation, diagnosis, or judgment about what gathered data *means* for a client's business, by the pull agent or anything else in this change — that's the analysis-job boundary above, and the pull agent's role stops at gathering.
- Reformatting the six "Challenge Library" documents into Claude Skill-format bodies. Whether that's even necessary is unresolved — see Open Questions.
- Defining a validation/testing methodology for the frameworks or skill themselves. Confirmed genuinely unsolved, including by Blu Mountain's own documentation — see Open Questions.

## Non-Negotiables

These apply to this change and to any future work that builds on it, the same way `CLAUDE.md`'s project-wide Non-Negotiables apply everywhere else in this repo. Reconfirmed 2026-08-27.

1. **No write operations against HubSpot, ever.** The original spec states access to HubSpot and every other source input is read-only with least-privilege read scopes; Airtable is the only read-write surface in this system. Applies to every future capability built on top of this one, not only to what's in this change.
2. **No HubSpot Private App tokens.** Explicitly excluded by the original spec — a Private App token cannot scale beyond a single account, and this project is multi-tenant by design (one shared Public App plus one shared MCP Auth App, installed separately per client via OAuth).
3. **The three analysis jobs — Funnel, Maintenance, KPIs & Reporting — will not be built under this plan.** Explicitly out of scope per `HubSpot_MCP_Server_Spec_v1.2.md` Section 1.2. Their shape and cadence are known (see Decisions below), but building them needs the original spec's scope boundary explicitly revisited, its own Anthropic API integration and credential, and its own separately-scoped change — none of which this plan authorizes.
4. **The other Intelligence System inputs will not be ingested**: Slack, ClickUp surveys, business descriptions, architecture guides, RSS, and the Architecture Guide diffing job. Excluded by that same spec line, alongside the analysis jobs. Each would need its own credential, its own ingestion path, and its own scope decision this plan doesn't make.
5. **No machine-learning training, fine-tuning, evaluation-dataset curation, or model hosting — ever, per client or per vertical.** "AI model" in this project means a Claude prompt/agent configuration, confirmed by Blu Mountain's own delivered documentation (which describes Claude skills and prompts throughout, never an ML training or evaluation pipeline). This was true even in the very first draft of this plan; restated here as a hard boundary, not a soft default, since an earlier "build and train per client" framing has resurfaced once already.
6. ~~**No per-client infrastructure, deployment, or Anthropic API credential.**~~ **Superseded 2026-09-01 by `openspec/changes/separate-vertical-client-agents`** — a deliberate, knowingly-made reversal, not a silent contradiction. That change's own `design.md` states explicitly: this was the third time the "per-client agent" framing surfaced (having already been rejected twice, once before this document was even written and once again during this document's own drafting, both recorded above), and this time it was confirmed on a direct leadership directive with full visibility into this prior rejection and its reasoning — not because the fallback condition below was ever met. What's *not* superseded: infrastructure and credential sharing stay unchanged — still one Anthropic API credential, still one shared deployment, for every vertical and every client. What changed is narrower than the original wording suggests: "one agent config per vertical, shared across every client" is no longer true — `separate-vertical-client-agents` persists one independently-editable agent template per vertical (`vertical_agent_templates`) *and* one persisted, independently-editable agent instance per client (`client_agent_instances`), superseding this section's data/context-only model. See that change's `design.md` for the full reasoning, alternatives considered, and the risk it explicitly accepts in doing this (echoing the very risk named two paragraphs below).
   <br>*(Original text, preserved for the historical record the paragraph above refers to):* "Per-client separation happens at the data/context layer — the onboarding profile and the staged Airtable data injected into a call — not by giving each client its own container, deployment, or credential. This is the same structural-isolation pattern already proven for HubSpot tenant data (`hub_id` enforced directly in every query, per-tenant encrypted tokens), not a new one invented for this capability. One Anthropic API credential, one agent config per vertical, shared across every client of that vertical."
7. **Every multi-tenant code path still requires an isolation test before it's considered done.** The standing project-wide rule from `CLAUDE.md`, restated here because it's the mechanism that makes #6 trustworthy rather than merely asserted — see `tenant-field-profiling`'s and `tenant-template-instantiation`'s isolation requirements for the concrete form this takes in this change.

## Decisions

**Corrected from the first draft: one shared, unmodified framework parameterized at runtime, not a persisted per-tenant copy.** The first draft of this design assumed a business-type template and a separate, persisted, human-reviewed tenant-specific *copy* of it. The delivered documentation describes something different: `Weekly_Diagnostic_Prompt` — the real runtime invocation of `account-diagnostic-SKILL` — is explicitly parameterized by injecting `{CLIENT_NAME}` and `{VERTICAL_FRAMEWORK_NAME}` at invocation time; "the prompt itself does not fetch inputs, it processes what is provided." Personalization happens *inside* each run through the framework's own detection logic (ACV band, motion type, retention pattern, marketplace side, etc.), computed fresh from real data every time — not baked into a stored, edited artifact ahead of time. This design now follows that pattern: the framework stays shared and unmodified; what's tenant-specific and stored is only the lightweight onboarding profile (which fields are confirmed relevant), not a copy of the framework or skill itself.

**Capability names retained from the first draft despite the corrected mechanism, to avoid inventing files an "update" pass isn't meant to create.** `analysis-template-schema` is now a storage/serving capability for content this project doesn't author; `tenant-template-instantiation` now produces an onboarding profile, not an instantiated copy. Both names are slightly misleading against what they now actually do. A rename is a reasonable future cleanup (via creating new spec files rather than editing these in place) but isn't required for the plan to be accurate — the requirements inside each spec file are what govern behavior, not the folder name.

**"Template" is Blu Mountain's word for something different — avoid the collision going forward.** Their `BluMountain_Template_Library_v1_3` catalogs 205 buildable deliverables (e.g., "Persona model," "Lifecycle model") across 8 delivery motions, each flagged applicable or not per vertical — a completely different concept from a "vertical framework." Prefer "vertical framework" or "framework" over "template" in any new writing about this capability, even though the existing spec/proposal filenames keep the original word.

**Tenant field-profiling reuses `sync/hubspot_client.py`'s existing pull mechanism, not a new one** — unchanged from the first draft. `pull_crm_objects()`/`discover_hubspot_schema` already return every real object type and its actual property set for a given tenant's connection; profiling is a read pass over that. Now additionally informed by each vertical framework's own "properties to trust by default" / "properties to treat as unreliable by default" guidance (present in every framework's schema-foundation section) as a starting point, rather than judging relevance from population statistics alone.

**Field-relevance filtering remains a flagged-for-review step, not a fully automatic one** — unchanged from the first draft, and the delivered documentation doesn't resolve this cleanly enough to change it. The frameworks describe an "onboarding analysis" step performed by "the bot" that identifies custom/integration properties, but never specify its mechanics in operational detail. Treating every framework-flagged field as auto-confirmed and everything else as auto-rejected is a reasonable machine-assisted starting point; final confirmation stays a human checkpoint until there's enough real onboarding history to know whether that judgment follows a reliable pattern.

**A third precedence layer exists that the first draft didn't account for.** `Blu_Operating_Principles.md` sits between framework detection and framework conditional gating: principles never change what a framework detects, but they bias which detected items get prioritized — with an explicit rule that framework logic wins if principles conflict with it, and principles win if a client's surface-level request conflicts with them. Any future consumer of a tenant's onboarding profile plus its framework needs room for this middle layer; this design doesn't build the layer itself (that lives in the skill/prompt content Blu Mountain owns), but the onboarding-profile schema shouldn't assume a two-layer (framework → output) pipeline.

**Delivery mechanism, previously an open question, is now known** (see Open Questions for what's still deferred): three jobs — Funnel (monthly or on-demand), Maintenance (bi-weekly), KPIs & Reporting (weekly, Monday AM) — plus ad-hoc on-demand triggering, all reading exclusively from the Airtable staging layer, never raw HubSpot at analysis time. A separate, adjacent "Architecture Guide" job does read workflow/report/dashboard configuration, but for documenting a client's HubSpot setup, not for the three analysis jobs this design's raw-data-only constraint governs — worth keeping distinct so the two are never confused.

**Scope boundary reconfirmed, not just inherited — 2026-08-27.** `HubSpot_MCP_Server_Spec_v1.2.md` Section 1.2 already excluded the analysis jobs and every other Intelligence System input (Slack, ClickUp, business descriptions, architecture guides, RSS) from this project, and this design's own Non-Goals already reflected that. What's new: that boundary was explicitly re-examined and reconfirmed, not just carried forward by omission, after this plan's own delivered documentation — which describes those excluded jobs and inputs in real detail — created real pressure to read "documented" as "in scope." It isn't. Nothing in the delivered documentation overrides or supersedes the original spec's scope line; it only explains what a future, separately-scoped change would eventually build if that line ever moves.

**"AI model" means a parameterized prompt, never a trained artifact — reconfirmed 2026-08-27.** An earlier framing of this plan ("build and train AI models per vertical, then per client") resurfaced outside this document; restated here for permanence: nothing in this design, corrected or original-draft, ever called for training or fine-tuning a model, per vertical or per client — see the Non-Goals above. What Blu Mountain's own documentation describes ("04 — Claude API" in `BM Intelligence System.md`: "every job makes one or more Claude API calls, each prefixed with a client context block and a job-specific prompt") is prompting with per-call context injection, the same mechanism this design already settled on, not training. Separately noted: an `ANTHROPIC_API_KEY` already exists in the repo's root `.env`. **Update 2026-08-28**: no longer inert — it's now wired into `config.py`/`docker-compose.yml` for the pull-agent capability below, the first real use of it in this project. Still not used for anything resembling the excluded analysis jobs.

**Per-client isolation is a data/context-layer concern, not an infrastructure or model concern.** Prompted by a "shouldn't each client have their own environment, not just their own prompt" question: yes, and that's what the onboarding profile mechanism already is. The framework/skill/prompt instruction text stays shared and unmodified across every client of a vertical; what's genuinely client-specific — and already isolated by construction, the same way HubSpot tenant data is (`hub_id` enforced directly in every query, per-tenant encrypted tokens) — is the onboarding profile and the staged Airtable data a future job would inject into each call. Nothing here calls for separate infrastructure, a separate deployment, or a separate Anthropic API credential per client; that would be a different, much larger architecture decision that no delivered documentation asks for.

**Where the three analysis jobs would live, if the scope boundary is ever revisited, is resolved as moot for now, not left open.** Previously an Open Question ("this repo, or a separate service?"); since the jobs aren't being built under the current scope decision, the question doesn't need answering today. If the boundary is revisited, whoever picks that work up decides it fresh, informed by the original spec's own "out of scope" framing (which suggests a separate service was always the intent) — this design doesn't pre-decide it.

**New capability confirmed in scope 2026-08-28: a per-vertical HubSpot data-gathering agent, "gathering, not analysis."** Directive: "take the SaaS models Blu Mountain provided and build an AI Agent for each one to automate the building of the GET requests to the HubSpot API to pull the data needed to perform the analysis" — clarified and confirmed the same day that this stays entirely on the data-*gathering* side of the boundary: the agent decides which of the existing allowlisted pull methods to call and with what parameters (informed by that vertical's framework's stated data needs), it never interprets what the returned data means for a client's business. That interpretation step is exactly the analysis-job boundary reconfirmed above and stays out of scope. "AI Agent" here means the Claude-API tool-use pattern (a loop where Claude selects and calls tools, all bounded by this project's existing `_is_read_safe`/`_is_safe_select` allowlist) — not a trained or fine-tuned model; see the "AI model means a parameterized prompt" decision above, which this is a direct extension of, now actually wired to the Anthropic API for the first time.

**Superseded 2026-09-01 — see Non-Negotiable #6 above for the full note.** **Shared agent per vertical is the starting architecture; per-client copies are a documented fallback, not adopted now.** One agent config per vertical (six total, mirroring the six stored frameworks), shared across every client of that vertical, parameterized per call by injecting that client's onboarding profile and goals — the same "shared instructions, isolated data" pattern as the rest of this design, extended to the tool-use layer. Per-client copies of each vertical's agent were considered and explicitly not adopted as the starting design: since no training or fine-tuning is involved either way (confirmed via research, see the fine-tuning findings folded in below), a per-client copy is functionally identical to the shared agent plus injected context — it adds no capability, only N-times the maintenance surface and N-times the isolation-testing surface. **Fallback condition, stated explicitly rather than left vague**: if real operational experience surfaces a genuine, structural reason the shared-agent approach can't isolate or serve one client correctly — not merely "it would feel safer to duplicate" — per-client copies remain a considered, available fallback, revisited then with the concrete failure in hand rather than adopted preemptively against a hypothetical one.

**Confirmed via research 2026-08-28: no path to fine-tuning or custom model training fits this project's scale.** Checked directly against official Anthropic documentation, AWS Bedrock's own docs, and Google Vertex AI's docs, not assumed: Anthropic's direct API offers no fine-tuning; AWS Bedrock does not support fine-tuning for any current-generation Claude model (Sonnet 5, Opus 4.8, Haiku 4.5) — its Claude fine-tuning path, where it existed, was for a now-superseded model generation and required Provisioned Throughput (no on-demand pricing) even then; Google Vertex AI offers no Claude fine-tuning at all. Anthropic's enterprise custom-training path is real but requires enterprise-scale commitment (deals "rarely start below $10M"), well outside this engagement's scale. This is why the pull agent (and everything else in this plan) is built on prompting plus per-call context injection, never training — not a preference, a constraint confirmed by direct research.

**Isolation requirements for the pull agent, agreed 2026-08-28 before implementation began** — see `specs/vertical-pull-agent/spec.md` for the formal SHALL/Scenario form. Six properties, four inherited directly from the isolation pattern already proven for `tenant-field-profiling`/`tenant-template-instantiation`, two genuinely new to this capability:
- Context assembly for one tenant reads only that tenant's own data (inherited pattern).
- A single API call never contains more than one tenant's data (inherited pattern).
- **New**: concurrent pulls for two different tenants never cross-write into each other's assembled context — a real risk once this runs on a schedule that processes multiple tenants around the same time, which the sequential-only isolation tests elsewhere in this project don't cover.
- **New**: every tool call the agent decides to make mid-loop is bound to the one tenant's vaulted HubSpot connection for that run, never a shared or ambient one — necessary because, unlike the fixed `pull_crm_objects()` pull, this agent decides at runtime what to call.
- A failed request's retry rebuilds context fresh rather than reusing a stale or wrong-tenant cached blob (inherited pattern).
- Every pull is attributable to the correct tenant in the audit log (inherited pattern).

**A vertical is required to produce an onboarding profile, scoped narrowly — 2026-08-31.** A profile produced with no vertical carries no framework guidance at all: every field lands in `needs_review`, which defeats the profile's actual purpose (cross-referencing a client's real fields against framework guidance). `produce_onboarding_profile` now resolves a vertical from an explicit argument, then from the tenant's own stored vertical, and refuses with a clear message if neither exists — the closest a backend function gets to "prompting" a human caller, since there's no interactive interface at this call site. Deliberately scoped narrowly, not applied project-wide: the raw HubSpot pull/Airtable staging layer (predates verticals entirely, shared by the whole project) and standalone field profiling (has real value even before a client's vertical is known, per its own original spec) both stay vertical-optional. An explicit `allow_unqualified=True` bypass exists for any future caller with a legitimate reason to proceed without one.

## Risks / Trade-offs

- **[Risk] Keeping the original capability names (`analysis-template-schema`, `tenant-template-instantiation`) despite their now-inaccurate implications could confuse a future reader who doesn't have this design doc's context.** → Mitigation: this document states the correction explicitly and permanently; a future rename is possible via `/opsx:continue`-created new spec files if it's ever worth the churn.
- **[Risk] Field-relevance judgment still isn't a defined, mechanical process** — Blu Mountain's own delivered documentation gestures at an "onboarding analysis" step without specifying it. → Mitigation: same human-review checkpoint as the first draft; revisit automation only once real onboarding history exists.
- **[Trade-off] This change still doesn't build the three analysis jobs that would make any of this observable end-to-end.** Accepted deliberately — folding job-building into this change would make it enormous and would build ahead of confirming the onboarding-profile mechanism actually works well against real client data first.
- **[Risk] The pull agent is the first thing in this project that spends real money per call and can behave non-deterministically.** Every other pull path is fixed, deterministic Python — same query every time, same cost every time. An agent that decides what to call can, in principle, loop longer or call more tools than a human-written pull would. → Mitigation: the agent's tool surface is restricted to the existing allowlisted, already-tested pull methods (nothing new it can reach that a human-written pull couldn't also reach), and its loop should be bounded (a maximum tool-call count per run) before this is considered production-ready — tracked in `tasks.md`.
- **[Risk] "Shared agent, per-client copies as fallback" could quietly become "build both" if the fallback trigger is treated loosely.** → Mitigation: the fallback condition above is stated as a concrete, structural failure, not a vague discomfort — revisit only against a real, specific instance where the shared approach demonstrably couldn't isolate or serve a client, not preemptively.

- **Should the six "Challenge Library" documents be reformatted into real Claude Skill-format bodies** (matching how `account-diagnostic-SKILL.md` already reads), or are they fine as reference-only catalogs the skill loads as context? Not decided by the delivered documentation. Current lean, not yet confirmed by Blu Mountain: keep as reference-only catalogs — structurally each is a lookup table (challenge → signal → response), not a set of operating steps, and `account-diagnostic-SKILL.md`'s own step 1 already treats framework-adjacent content this way.
- **What validation/testing methodology proves a vertical framework or the skill actually works?** Confirmed genuinely unsolved — Blu Mountain's own `Blu_Operating_Principles.md` lists quantitative validation (expanding from 4 to 36+ tracked clients) and outcome correlation as pending, not implemented, work. This project can't resolve this alone; it likely needs a decision from Blu Mountain's own strategy side.
