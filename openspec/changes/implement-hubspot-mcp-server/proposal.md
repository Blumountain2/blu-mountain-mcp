## Why

Blu Mountain needs a single service that reads read-only data from every client's HubSpot portal (one shared HubSpot Public App, OAuth v3 with PKCE, installed separately per client) and stages it, alongside Sybill call transcripts, into Airtable for downstream analysis jobs and dashboards to consume. This is input number two of Blu Mountain's Intelligence System, specified in `context/Hubspot/HubSpot_MCP_Server_Spec_v1.2.md`. Separately, Blu Mountain staff need a live, interactive way to query one client's HubSpot data through Claude Desktop, Claude Code, or Claude Cowork — identically from any of the three — authenticated via Google Workspace, one tenant at a time. The repository has been cleaned of an unrelated template and one piece is built and verified (direct Google/Microsoft staff/owner authentication, a distinct and simpler surface from the live session), but the actual HubSpot integration, the token vault, the Airtable staging, the Sybill ingestion, and the live session do not exist yet. This change builds them.

## What Changes

- Register a HubSpot Public App and build the OAuth v3 + PKCE install/callback flow so each client portal can authorize the shared app (Flow B).
- Build a per-tenant token vault: Postgres storage, AES-256 encryption with a key derived per tenant (not one shared key), proactive refresh, advisory-lock-serialized concurrency, and a HubSpot uninstall webhook.
- Build the per-tenant HubSpot data-pull layer covering the read-only object set in spec Section 4.4 (contacts, companies, deals, tickets, line items, products, calls, emails, meetings, notes, tasks, plus reference objects).
- Build the scheduled Airtable staging job that normalizes pulled HubSpot data, tags every record by client, and writes it on an interval.
- Build the Sybill webhook receiver: signature validation, normalization, and staging into Airtable, tagged by client, built against Sybill's own published schema. **Still unresolved** (spec open item #6): whether webhook delivery is actually what Sybill uses is not confirmed by the client, only assumed per the spec's own stated assumption — see design.md's Risks section, which quotes the client's actual (ambiguous) answer. This receiver is built and ready, not proof the assumption is correct.
- Harden security controls: per-tenant Postgres-based rate limiting, a persistent audit log (60-day retention), and a credential-hygiene sweep across every code path.
- Verify tenant isolation by test, not by inspection, at a 100% pass rate, per the client's explicit instruction that client data must never cross-pollinate. This gates every other capability's completion.
- Direct Google/Microsoft staff/owner authentication (`gateway/session/staff_auth.py`) already exists and is verified working. Resolved by this change: no planning document identifies a consumer for it distinct from the live session below, so it's unhooked from `main.py` (`/staff/me` removed) and kept in the codebase, unwired, for a possible future non-MCP consumer (e.g. a web dashboard). See design.md's decision log.
- Build the live session: FastMCP's own OAuth Proxy wraps one manually registered Google Workspace OAuth client, presenting a Dynamic Client Registration-compliant, Protected Resource Metadata-serving interface so Claude Desktop, Claude Code, or Claude Cowork can connect the same way they would to any other remote MCP server — identically from any of the three. It issues its own audience-scoped JWT to the connecting client rather than forwarding Google's token, enforces the Google Workspace domain allowlist on every login, and reuses the shared `hubspot-data-pull` layer to serve one tenant's data at a time, gated by a Postgres staff-to-tenant permission table and an explicit tenant-selection step whenever staff have access to more than one.

**No longer part of this project**: WorkOS. It was the original choice for the live session's identity-broker layer, superseded once FastMCP's own OAuth Proxy was confirmed to close the same gap (DCR compliance, audience-scoped tokens) without a third-party broker. See `context/Hubspot/REPO_CLEANUP_DECISIONS.md` for the full history.

## Capabilities

### New Capabilities

- `hubspot-oauth`: the HubSpot Public App install/callback flow, PKCE, state validation, token exchange, and the app-credential/tenant-token separation the spec requires.
- `mcp-auth`: a second, parallel install/callback flow for the MCP Auth App (spec Section 4.1) — discovered during implementation, not anticipated at proposal time: `mcp.hubspot.com` is its own OAuth resource server and rejects the Public App's token, so reading any HubSpot data at all requires this second credential, installed into the same portal right after the Public App.
- `token-vault`: per-tenant encrypted token storage, per-tenant key derivation (HKDF from a single root key), the access-token cache, proactive refresh, advisory-lock concurrency control, and HubSpot uninstall handling via webhook. Covers both vaulted credentials (the Public App's and the MCP Auth App's) via the same parameterized implementation.
- `hubspot-data-pull`: the per-tenant client that reads HubSpot's remote MCP endpoint using the vaulted token, scoped to the in-scope read-only object set, shared infrastructure for both the scheduled staging job and any future live session.
- `airtable-staging`: the scheduled job that normalizes HubSpot data per object type, tags every record by client, and writes it into Airtable on an interval.
- `sybill-ingestion`: the webhook receiver that validates Sybill payload signatures, normalizes call-transcript data, and stages it into Airtable, tagged by client.
- `security-hardening`: per-tenant rate limiting, the persistent audit log, and the credential-hygiene guarantees (no token or secret ever reaches a log line, prompt, or tool description).
- `tenant-isolation`: the test suite proving no cross-tenant data or error leakage, across every other capability, at a 100% pass rate, the non-negotiable gate for the whole project.
- `live-mcp-session`: the live, interactive MCP session for Blu Mountain staff — reachable identically from Claude Desktop, Claude Code, or Claude Cowork — built on FastMCP's OAuth Proxy wrapping one manually registered Google Workspace OAuth client, Google Workspace domain allowlisting, the staff-to-tenant permission table and tenant-selection enforcement, and per-access audit logging by staff identity and tenant.

### Modified Capabilities

None. No existing specs in `openspec/specs/` yet; the direct Google/Microsoft staff auth capability already built (`gateway/staff_direct_auth.py`, `gateway/main.py`) is being documented as a baseline capability in this change's specs, not modified.

## Impact

- **New code**: `gateway/main.py` (HubSpot OAuth routes, staging scheduler, Sybill webhook, FastMCP OAuth Proxy mount and tenant-selection routes), plus new modules for the token vault, HubSpot pull client, Airtable client, rate-limiting/audit-log tables, and the staff-to-tenant permission table.
- **Database**: new Postgres schema (tenants, tokens, `mcp_tokens`, rate-limit counters, audit log, staff-tenant permissions), backed by the already-running `postgres` service in `docker-compose.yml`.
- **External dependencies**: ~~HubSpot Developer account and Public App registration (blocked on real credentials)~~ **Resolved: real Public App and MCP Auth App credentials registered, both installed and confirmed working end to end against two real test portals** (see design.md's decision log). ~~Airtable base and Personal Access Token (blocked on schema design)~~ **Partially resolved: the Personal Access Token is provisioned; the schema is designed and built; the actual staging base still needs creating** (see `context/BLOCKERS.md`). ~~Sybill webhook secret (blocked on Wednesday's meeting outcome)~~ **Partially resolved: secret provisioned, receiver built and tested against Sybill's published schema — but whether webhook is actually Sybill's real delivery mechanism remains unconfirmed by the client** (spec open item #6; see design.md's Risks section for the actual, ambiguous client answer). A Google Cloud OAuth 2.0 client registered for FastMCP's OAuth Proxy (`FASTMCP_GOOGLE_CLIENT_ID`/`FASTMCP_GOOGLE_CLIENT_SECRET`) remains the one still-pending credential, distinct from the direct-auth path's own Google client.
- **Existing code touched minimally**: `gateway/main.py` grows to host these new routes; the `/staff/me` endpoint that previously lived there has been removed (see the `session/staff_auth.py` decision above). `gateway/requirements.txt` already has the needed dependencies (`fastmcp`, `asyncpg`, `apscheduler`, `pyairtable`, `cryptography`) from earlier planning.
- **Out of scope for this change**: the analysis jobs and dashboards that read from Airtable, any other Intelligence System input (Slack, ClickUp, business descriptions, architecture guides, RSS), and whether Microsoft 365 needs the same OAuth Proxy treatment for the live session (open question, Google only for now).
