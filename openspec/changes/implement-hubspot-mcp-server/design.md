## Context

The repository was originally a generic, copy/pasted "MCP Gateway" template (Keycloak/Google/Microsoft SSO, Open Policy Agent RBAC, Redis, a Prometheus/Grafana/Loki stack, fronting demo backend servers). That template was removed; see `context/Hubspot/REPO_CLEANUP_DECISIONS.md` for the full rationale. The actual target, per `context/Hubspot/HubSpot_MCP_Server_Spec_v1.2.md`, is a multi-tenant service: Blu Mountain operates one shared HubSpot Public App, each client authorizes it into their own portal via OAuth v3 + PKCE, and the service vaults per-tenant tokens and stages HubSpot and Sybill data into Airtable.

One capability is already built and verified: direct Google/Microsoft JWT staff/owner authentication (`gateway/session/staff_auth.py`, `gateway/main.py`), confirmed working by actually building the container and testing missing, malformed, wrong-issuer, and invalid-signature tokens, not just by inspection. Two real bugs were found and fixed during that verification (an unhandled exception on a malformed token, and a `cryptography` version conflict between the pinned range and an earlier `workos` dependency, since removed). Everything else, HubSpot OAuth, the token vault, the data pull, Airtable staging, Sybill ingestion, and the live session, does not exist yet.

A separate capability, a live interactive session for Claude Cowork, was originally designed around WorkOS after two auth flow diagrams surfaced a requirement the written spec never stated. Rereading the spec's FR-7 through FR-10 directly confirmed none of them require a live session to exist, they describe properties the tenant-scoped pull mechanism itself needs, so this capability is not required by the written spec, only by the diagrams. It was deferred for a time on that basis, then reactivated once the client's own "Build Prerequisites" document called for a Google Cloud OAuth client and research confirmed FastMCP ships its own OAuth Proxy: it presents a Dynamic Client Registration-compliant, Protected Resource Metadata-serving interface to MCP clients (Claude Desktop, Cowork, Code) while using one manually pre-registered Google Workspace OAuth client underneath, and issues its own audience-scoped JWT rather than forwarding Google's token. That closes the exact gap WorkOS was originally chosen for, without a third-party identity broker, so WorkOS is now fully out of scope, not merely deferred. See `context/Hubspot/REPO_CLEANUP_DECISIONS.md` for the full staged history.

## Goals / Non-Goals

**Goals:**
- Implement every functional requirement (FR-1 through FR-13) and security control (SC-1 through SC-10) in the written spec, each backed by a passing test, not a claim.
- Keep every client's data strictly isolated in a shared Postgres instance, proven by test at a 100% pass rate, per the client's explicit instruction that data must never cross-pollinate.
- Build the scheduled Airtable staging pipeline (HubSpot pull plus Sybill ingestion) as the actual deliverable other Intelligence System components consume.
- Build the live session on FastMCP's OAuth Proxy wrapping Google Workspace, so Blu Mountain staff can query one client's HubSpot data at a time through Claude Desktop, Claude Code, or Claude Cowork — identically from any of the three — with every interactive access attributable to a specific staff identity and tenant.

**Non-Goals:**
- The analysis jobs, dashboards, or any other Intelligence System input (Slack, ClickUp, business descriptions, architecture guides, RSS).
- Any write operation against HubSpot, or a HubSpot Private App flow. Read-only access with least-privilege scopes is a hard boundary, not a default.
- Building or hosting a general-purpose identity provider. The live session's FastMCP OAuth Proxy wraps one manually pre-registered Google Workspace OAuth client rather than implementing OAuth server-side logic of its own; direct Google/Microsoft verification (`session/staff_auth.py`) similarly validates tokens issued by those providers directly, it does not issue or broker them.
- Deciding whether Microsoft 365 needs the same OAuth Proxy treatment as Google for the live session. The client's own prerequisites document only details Google; tracked as an explicit open question below, not assumed either way.

## Decisions

**Single Postgres instance, no Redis.** One encrypted Postgres instance backs the token vault, the access-token cache, refresh coordination (advisory locks), and rate-limit counters. Considered Redis for caching/locks (the original template used it): rejected because a single Postgres store removes the operational cost of a second service at this project's scale (about 50 tenants currently), and the spec's own reference stack calls Redis "an optional upgrade only if many server instances with high refresh concurrency later warrant it," not a baseline requirement.

**Per-tenant encryption keys derived from one root key, not one shared key.** Each tenant's AES-256 key is derived from a single root key (`APP_ENCRYPTION_KEY`) via HKDF, using `hub_id` as derivation context, rather than encrypting every tenant with the same key. This was corrected mid-project after an earlier version of this plan used one shared key: the spec states "tenant-scoped decryption keys" three separate times (Sections 1.3, 5, 9), and a single shared key means one compromise exposes every tenant at once, while derived per-tenant keys contain a compromise to one tenant. Only one secret needs to be managed operationally either way.

**Portal-level authorization, not per-user.** One HubSpot OAuth authorization per client portal (`hub_id`), no per-user token indexing on the HubSpot side. Confirmed by the client directly (spec open item #2) rather than assumed.

**FastMCP's OAuth Proxy, wrapping Google Workspace, powers the live session; WorkOS is fully out of scope.** FastMCP's OAuth Proxy bridges DCR-incompatible providers like Google by presenting a DCR-compliant, Protected Resource Metadata-serving interface to MCP clients while using one manually registered upstream OAuth client, and issuing its own audience-scoped JWT (token factory pattern) rather than forwarding Google's token, this is what satisfies the no-token-passthrough non-negotiable for this path, Google's token never leaves the proxy. This closes the same gap WorkOS was chosen for in an earlier version of this plan, without a third-party identity broker, so WorkOS has been removed entirely (`workos` dependency, `WORKOS_*` variables), not merely deferred.

**The live session's FastMCP OAuth Proxy stays Google-only; Microsoft 365 parity was considered and explicitly not built.** The client's prerequisites document only ever specified Google, and real Google credentials are the ones already in progress, so `live-mcp-session` builds and stays on `GoogleProvider` alone — no `AzureProvider`/Microsoft Entra wiring is added alongside it. This decision is scoped narrowly to the live session's OAuth Proxy; it does not affect `session/staff_auth.py`'s separate, unhooked direct-verification surface below, which keeps its existing Google *and* Microsoft support unchanged, since a future non-MCP consumer of that module (e.g. a dashboard) may specifically need staff to sign in with either provider.

**Direct Google/Microsoft JWT verification kept in the codebase, but unhooked from `main.py`.** `gateway/session/staff_auth.py` verifies an already-issued Google or Microsoft token directly, a plain API guard rather than an MCP resource server. It predates the discovery that FastMCP's OAuth Proxy was buildable, and was carried for a while as an open question (does it remain distinct, or was it an earlier, narrower expression of the same need the live session now covers). Resolved: a deep review of every planning document (the spec, this design doc, the implementation plan, `REPO_CLEANUP_DECISIONS.md`) turned up no identified consumer for it distinct from what the live session already does; every mention of it frames it as a stand-in for the same underlying need, never a second one. `main.py` no longer routes to it (`/staff/me` removed, `StaffDirectAuthenticator` no longer instantiated), and `session/__init__.py` no longer re-exports it. The module itself is not deleted: it stays in the repository, importable directly as `session.staff_auth`, in case a future non-MCP consumer (e.g. a web dashboard) needs a plain bearer-token verifier. Kept rather than deleted because it's already real, verified work, and costs nothing to leave dormant.

**Tenant access is default-open, explicitly restrictable — not an allow-list.** Revised from an earlier allow-list design (a table granting each staff member specific tenants) after review found the client's own spec (`HubSpot_MCP_Server_Spec_v1.2.md`) never actually scopes staff-side access at all — that spec is silent on the live session entirely, and the allow-list's specific shape was Gumpper's own implementation choice, not a client requirement. Given Blu Mountain has no staff role system (owner/admin/sales) and no admin UI, an allow-list means every new hire or new client needs a manual Postgres grant before anyone can use them together — real operational friction for a boundary that (since access is strictly read-only) exists for internal confidentiality between Blu Mountain's own clients, not data-integrity risk. Instead, `staff_tenant_restrictions` is a deny-list: any staff member who signs in successfully has access to every installed tenant by default, unless a row explicitly restricts them from a specific one. This keeps the door open to restrict a specific client later (e.g. a confidentiality requirement) without requiring day-one administration for the common case. A session with more than one permitted tenant must still have exactly one explicitly selected before the live session serves any HubSpot data, since the underlying `hubspot-data-pull` layer always operates against exactly one tenant's vaulted token at a time — that part of the design is unchanged.

**Every interactive live-session access is audited by staff identity and tenant.** This is the only record that can attribute a HubSpot read to a specific person, since HubSpot itself only ever sees the one shared app credential, not an individual staff member. Reuses the same Postgres audit log the scheduled staging job writes to, distinguished by access type. Denials are audited too, not only successful access — a rejected sign-in, a rejected tenant selection, and a staff member with no permitted tenant at all each get their own audit entry, since a denied attempt against a confidentiality boundary is exactly what this log exists to attribute to a person.

**Hardening pass on the default-open model, found via a multi-agent code review before this branch's first push to `dev`.** Several real gaps surfaced once the model above was actually reviewed end to end, all fixed together:
- An empty or unconfigured `FASTMCP_ALLOWED_GOOGLE_DOMAINS` now fails closed (rejects every sign-in) instead of failing open (admitting every domain) — under the old allow-list this misconfiguration was harmless, since a stranger still hit an empty grant table; under default-open it's the only gate, so the safe default flipped.
- `staff_tenant_restrictions.hub_id` now references `tenants(hub_id)`, so a mistyped `hub_id` (there's no admin UI; restrictions are hand-typed SQL) fails loudly at insert time instead of silently becoming a permanent no-op that never matches anything in the installed set.
- `.lower()` calls in `_require_staff_identity` were changed from `.get(key, "").lower()` to `(.get(key) or "").lower()` — the former's default only applies when a claim key is *absent*; a key present with value `None` reached `.lower()` directly and crashed with `AttributeError` instead of cleanly rejecting.
- `_permitted_tenants` collapsed from two sequential queries (shared `get_installed_hub_ids()` plus a restrictions query, reconciled in Python) into one SQL statement, and `_resolve_selected_tenant` now gathers its two independent reads concurrently instead of awaiting them back to back — the auto-select path also no longer re-derives and re-validates the same permitted set a second time through `select_tenant_internal`. This knowingly reintroduces the `install_status = 'installed'` predicate in a second place (also in `get_installed_hub_ids()`, still used by the scheduled sync job) — a deliberate, narrow trade of that duplication for materially fewer Postgres round trips on the live session's hot path.
- The audit-log purge job's own failure-reporting call (`record_audit`) is now guarded by its own nested try/except, and `sync/airtable_staging.py`'s per-tenant failure handler got the same treatment — without it, a Postgres outage during the *failure* path would itself raise, silently aborting the purge job's visibility or, worse, the entire remaining sync cycle for every other tenant.
- The purge job now also runs once directly at startup, not only on its 24-hour interval — confirmed directly against this project's installed `apscheduler` version that `IntervalTrigger` schedules its first fire one full interval out, not immediately, so a service restarted more often than every 24 hours could otherwise go its entire life without the purge running once.

**HubSpot uninstall detection via a signed webhook, not polling.** Spec Section 2.1 names "the Webhooks API" as a required Public App capability. SC-5 requires webhook signature validation with a 5-minute replay window, distinct from Sybill's own webhook (SC-9), which mirrors the same basis. This was caught during a requirements audit; an earlier version of this plan had no explicit mechanism for uninstall detection at all.

**Sybill ingestion assumed to be webhook-based, pending confirmation.** Spec open item #6 is unresolved as of this change; the spec's stated assumption is webhook delivery. If the pending client meeting determines otherwise, the `sybill-ingestion` capability's spec and tasks will need revision, tracked as an explicit risk below.

**Two redirect routes compensate for discovery URLs that don't resolve correctly, given how this app is mounted.** `main.py` mounts the live session under `/mcp` inside a larger FastAPI app (`app.mount("/mcp", mcp_app)`), alongside `/install`, `/callback`, `/health`, and the webhook routes. Both gaps were found by tracing real request logs from a live MCP Inspector session (browser UI, not just `curl` speculation), and each was verified by introspecting the mounted app's own route table directly before writing a fix — not guessed.

1. **Protected-resource metadata (RFC 9728).** FastMCP registers this route with its own path suffix baked in (`/.well-known/oauth-protected-resource/mcp/`, derived from `base_url`'s path). The real, correctly-populated document is reachable at `/mcp/.well-known/oauth-protected-resource/mcp/` (outer mount prefix plus that internal suffix). But the `WWW-Authenticate` header on `/mcp`'s `401` challenge advertises the URL *without* the outer `/mcp` prefix — FastMCP has no way to know about a mount decision made entirely in `main.py` — so it 404s for any real client (confirmed: Inspector's "Dynamic Client Registration rejected (HTTP 404)"). Fixed with a redirect from the broken advertised path to the real one.
2. **Authorization-server metadata (RFC 8414).** The metadata is only reachable at `/mcp/.well-known/oauth-authorization-server` (outer mount prefix applied to FastMCP's own plain-registered route) — but that combination isn't a standard discovery pattern, it's an accident of how the mount and FastMCP's routing happen to line up. RFC 8414's actual convention for an issuer with a path component (ours is `http://localhost:8888/mcp`) is to insert the path *after* the well-known segment: `/.well-known/oauth-authorization-server/mcp`. Real clients request exactly that (confirmed against the same Inspector session), and it 404s. Fixed the same way, with a redirect from the standard path to the one that actually works.

Neither is fixable via a `GoogleProvider`/`OAuthProxy` config value, since both are fundamentally about a mount applied outside FastMCP's own knowledge. Confirmed resolved end to end via `curl` tracing the full chain and a live Inspector CLI session reaching `auth_required` (the correct next stop — needs a browser and the still-pending real Google credentials) with no discovery or DCR failure in between.

**`mcp.hubspot.com` requires a second, separate "MCP Auth App" credential — added as `auth/mcp_auth.py`, mirroring `auth/hubspot_oauth.py` rather than merging into it.** A live 401 from the data pull (real HubSpot Public App and portal install, both already working) revealed that `mcp.hubspot.com` is its own OAuth resource server (confirmed via its own RFC 9728/8414 metadata: distinct issuer, `/oauth/authorize/user`, `/oauth/v3/token`) and does not accept the Public App's CRM-scoped token — matching the spec's own Section 4.1, which this project's earlier build had not yet implemented. Built as a fully parallel install/callback flow (`/install/mcp-auth`, `/callback/mcp-auth`) against a new `mcp_tokens` table (FK to `tenants(hub_id)`, so it can only be installed after the Public App for the same portal — enforced as an explicit `409`, not a raw FK-violation `500`), and a second `TokenVault` instance (`mcp_vault`) reusing the exact same advisory-lock/cache/proactive-refresh logic against a different table and refresh endpoint. `sync/hubspot_client.py` now reads from `mcp_vault`, not the Public App's `vault`.

**hub_id for the MCP Auth App comes directly from the token-exchange response body — confirmed live, not guessed.** The original implementation assumed (per this project's own then-unconfirmed docstring) that a separate introspection call would be needed to learn `hub_id`, since the Public App's own `GET /oauth/v1/access-tokens/{token}` lookup is on a different issuer. Confirmed live against a real install that `mcp.hubspot.com`'s introspection endpoint (`/oauth/v3/token/introspect`) returns only RFC 7662's minimal `{"active": true/false}` — no portal identifier at all — so it was never a viable source. The real answer is simpler: the token-exchange response body itself carries `hub_id` directly. The access token itself is also confirmed opaque, not a JWT (one segment, not three), ruling out claim-decoding as a source too. `mcp_auth.py` was simplified accordingly — no introspection call is made at all.

**The core CRM object set (contacts, companies, deals, tickets, etc.) has no per-object tool on `mcp.hubspot.com` — confirmed live, not assumed from the spec's object list.** `hubspot_client.py`'s original design assumed per-object tools discoverable via `list_tools()` (e.g. a `list_contacts`-shaped name), matching the six real marketing/analytics tools that *do* exist that way. The entire core object set instead goes through exactly one generic tool, `query_crm_data`, which takes a raw SQL-like string (HubSpot's own constrained dialect: no JOIN/UNION/subqueries/CTEs/aliases, one object type per query). Real object-type names were confirmed via `discover_hubspot_schema`'s `GET_OBJECT_TYPES` rather than guessed from the spec's plain-English names — one materially differs (`MEETING_EVENT`, not `MEETING`). ~~The spec's `teams` reference object has no corresponding queryable type at all in the real schema, a known unfilled gap rather than a wrong guess.~~ **Resolved by a later decision below: `teams` is real, just not through `query_crm_data` — it's read via the separate `get_organization_details` tool instead, found via a full audit of every discovered tool that this project's own logging had been silently excluding.** Because tool-name filtering can't gate `query_crm_data` (the object type lives in the SQL text, not the name), it's handled by a dedicated `pull_crm_objects()` path: the SQL is always a fixed `SELECT * FROM {TYPE}` authored in code, never passed through from a caller, and is still checked by `_is_safe_select()` (rejects anything but a single plain `SELECT`, no stacked statements) as defense in depth even though the SQL is never externally sourced — the same "don't rely on scope alone" posture already established for the `tickets` read-verb allowlist. Confirmed live that every one of `CRM_OBJECT_TYPES` (`CONTACT`, `COMPANY`, `DEAL`, `TICKET`, `LINE_ITEM`, `PRODUCT`, `CALL`, `EMAIL`, `MEETING_EVENT`, `NOTE`, `TASK`, `USER`) correctly shows `writeAccess: REQUIRES_PERMISSION_MODIFICATION` under the "View Only" grant chosen at install — an independent, HubSpot-side confirmation that the read-only-absolute non-negotiable holds at the permission layer, not just in this project's own code.

**None of HubSpot's real MCP tools declare an `outputSchema` — confirmed live across all 20 discovered tools, not assumed.** `pull_object()`'s original `result.data if hasattr(result, "data") else result` was silently wrong for every tool call in production: `hasattr(result, "data")` is always `True` (FastMCP's `CallToolResult` always has the attribute), but the value itself was always `None`, since none of these tools populate FastMCP's structured-output path. The real payload is JSON text inside `result.content[0].text` instead — confirmed against `search_owners`' plain JSON object and `query_crm_data`'s distinct, more complex shape (a citation-oriented envelope: `{"results": [{"content": "<json-encoded record>"}, ...], "instructions": "..."}`, where `instructions` is LLM-facing guidance, not data, and each record is itself double-JSON-encoded). Fixed with `_extract_result()` (falls back to parsing `result.content` when `.data` is empty) and a `query_crm_data`-specific `_unwrap_query_crm_data()` that flattens its distinct envelope shape into plain record dicts. Found and fixed before this ever reached a real scheduled sync — every prior "successful" pull in this project returned `None` for every object.

**First real, live, end-to-end confirmation of the entire pull path (2026-08-12), against the real test portal (`hub_id=148997330`).** Both installs (Public App, MCP Auth App) completed for real; `pull_crm_objects()` returned real records matching the test portal's known seed data exactly (2 sample contacts, 1 "HubSpot" company, sample call/email/meeting/task records, 3 real users including `evan@gumppergroup.com`), with `DEAL`/`TICKET`/`LINE_ITEM`/`PRODUCT`/`NOTE` correctly empty (none created yet in this fresh account). A live `token_vault.refreshed` log line during this run is the first direct evidence (not just RFC 8414 metadata inference) that the MCP Auth App's refresh-token grant actually works unattended against the real endpoint. Four marketing/analytics tools (`get_campaign_attribution_reports`, `get_content_analytics_report`, `get_marketing_email_analytics`, `read_campaign_data`) failed on this first pull with parameter/authorization-shaped errors — correctly isolated per-tool by `pull_all()`'s existing error handling, not a blocker for the core object set this project exists to sync. **All four are now resolved, see the later decisions below** — two were genuine missing-parameter bugs, two needed a real Enterprise-tier test account to verify rather than more code.

**Test suite isolated onto its own Postgres database (`mcp_test`), not the same database `docker compose up`'s dev stack uses.** `gateway/tests/conftest.py`'s `_pool` fixture truncates every table it touches after each test; running the suite against the same `mcp`/`postgres-data` volume the real dev stack uses destroyed a real, verified tenant install twice in one session before this was caught. Fixed by having the `_schema` fixture create and use a separate `mcp_test` database (via a maintenance connection to Postgres's own always-present `postgres` database) automatically on first run — still a real Postgres instance, per this project's own testing philosophy, just genuinely isolated data.

**A full audit of all 20 real MCP tools against spec Section 4.4 turned up a real observability gap, not just missing coverage.** `list_read_only_tools()`'s logging only ever covered two buckets — write-shaped names and read-safe-but-unrecognized names — leaving a third case, read-safe names that simply don't match any in-scope keyword, completely unlogged. Seven of the 20 real tools fell into this silent gap (`get_conversation_channel_metadata`, `get_properties`, `get_crm_objects`, `search_conversations`, `search_crm_objects`, `get_organization_details`, `search_properties`), and one of them, `get_organization_details`, turned out to be the real, working path to the spec's "teams" reference object — the exact thing an earlier decision above recorded as "a known, currently-unfilled gap in the real schema." It was never unfillable, it was unnoticed. Fixed by restructuring `list_read_only_tools()` into a single pass with a third, always-logged bucket (`hubspot_pull.out_of_scope_tools_excluded`, info level) — confirmed live that the other six really are out of scope (`search_conversations`/`get_conversation_channel_metadata` are HubSpot's separate inbox/live-chat feature, never named in Section 4.4; `get_properties`/`search_properties`/`get_crm_objects`/`search_crm_objects` are metadata/lookup tools redundant with `query_crm_data`'s existing full-object-set coverage), while `get_organization_details` (`IN_SCOPE_OBJECT_KEYWORDS` gained "organization") is now pulled for real, resolving the "teams" gap.

**"Segments," "landing pages," and "blog posts" (all spec-named reference objects) are plain queryable `query_crm_data` object types too, confirmed live — `OBJECT_LIST`, `LANDING_PAGE`, `BLOG_POST` added to `CRM_OBJECT_TYPES`.** Landing pages looked, at first, like they'd need the same kind of dedicated action-level guard `query_crm_data` itself needed (HubSpot's `manage_landing_page` tool mixes real read actions — `MODULES`, `TEMPLATES`, `FORMS` — with write actions behind one `action` parameter). Checking `discover_hubspot_schema`'s object-type list first (the same place `CRM_OBJECT_TYPES`'s existing entries came from) showed `LANDING_PAGE` and `BLOG_POST` are both already plain, directly queryable types — confirmed live with real `SELECT * FROM LANDING_PAGE`/`BLOG_POST` calls — so neither needed `manage_landing_page`'s more complex, mixed-action tool at all. `OBJECT_LIST` (HubSpot's internal name for "Lists") resolves the spec's "segments" the same way, confirmed live returning real list records (workflow enrollment lists, `ALL_OPEN_TICKETS`, etc.) from the test portal.

**`get_content_analytics_report` and `get_marketing_email_analytics` were fixed; `get_campaign_attribution_reports` and `read_campaign_data` needed a real Enterprise-tier test account to actually verify, not more code.** All four had failed with parameter-shaped errors during the first live pull. Inspecting each tool's real schema showed two genuinely different root causes: the first two have a truly required field (`mode`) their schema rejects an empty call without, fixed with `_DEFAULT_TOOL_PARAMS` (mode=`TOTALS`, and a rolling 30-day `OVERVIEW` window respectively) and confirmed live returning real, valid (if empty) responses. The other two's real failure was `"Not Authorized"`/a missing `campaignCrmObjectId` this test portal had no accessible campaign to supply — traced to `discover_hubspot_schema` showing `CAMPAIGN`'s `readAccess` as `REQUIRES_ACCOUNT_MODIFICATION` on that specific portal, an account-tier gate, not a parameter gap. This was initially recorded as a portal-tier limitation not worth building unverifiable code against. A second HubSpot developer test account (`hub_id=149094230`, Enterprise tier — HubSpot's own developer test accounts include a 90-day trial of enterprise features by default, confirmed via developers.hubspot.com's own documentation, not assumed) with one real campaign created in it (`hs_object_id=1321946824900`) confirmed `CAMPAIGN` shows `readAccess: AVAILABLE` there, and both tools work correctly once called right: `get_campaign_attribution_reports` needs `metrics` (a truly required field despite an empty `required: []` in its schema) and `hasReadToolInstructions: true` (skips a one-time instructions round-trip aimed at an LLM caller, not useful for this scheduled job's always-the-same call) — added to `_DEFAULT_TOOL_PARAMS`; `read_campaign_data` needs a real `campaignCrmObjectId` for every operation, so it can't take a single fixed default the way the others can — handled by a new `pull_campaign_data()` method that enumerates real campaign IDs via `query_crm_data` first, then calls once per campaign, with `read_campaign_data` itself excluded from the generic dynamic-tool loop (`_PER_ITEM_TOOLS`) since its name would otherwise pass the read-verb/in-scope filter and get called there too, always failing. Confirmed live end to end against the new account: `get_campaign_attribution_reports` returns `COMPLETED`, `pull_campaign_data()` returns real (if zero-valued, since the campaign has no deals/contacts yet) engagement metrics keyed by the real campaign ID. Confirmed the original test account (`148997330`, without Campaigns enabled) still degrades gracefully — both tools correctly marked `{"error": "pull_failed"}`, no crash, isolated per-tenant exactly as designed.

**Two HubSpot developer test accounts now exist for this project, deliberately at different tiers.** `148997330` (the original) does not have Campaigns/Marketing Hub enterprise features enabled; `149094230` does, created specifically to verify the two account-tier-gated tools above. Both are free — HubSpot's developer test accounts cannot be upgraded to paid status (confirmed via HubSpot's own account-types documentation), so a fresh test account, not an upgrade, is the correct way to get trial access to a different feature set. Real installs (Public App + MCP Auth App) completed on both.

**Install success/error pages redesigned from raw JSON to styled HTML — a real UX gap for a human-facing OAuth flow, not a backend API.** `/callback` and `/callback/mcp-auth` originally returned `{"status": "installed", "hub_id": "..."}` and FastAPI's default `{"detail": "..."}` error shape — both fine for a programmatic caller, confusing for the actual real-world caller: a portal admin's browser, redirected here by HubSpot at the end of a consent flow, with no other consumer of this response ever identified. Replaced with `auth/pages.py`, a small dependency-free HTML renderer (no templating engine needed for two static pages): a success page (green check, portal ID, and — when a next step exists — that step's absolute URL as a clickable link plus a Continue button, both derived from the incoming request's own host so they're correct in any environment) and a matching error page (red icon, a plain-language message, a Start Over link back to the failed step) for all seven error paths across both callbacks. Every one of these previously raised `HTTPException`; all now `return` a rendered page directly, scoped to just these two routes so no other route's JSON error behavior changed.

## Risks / Trade-offs

- **[Risk] Sybill's actual delivery mechanism (webhook vs. polling) is still unconfirmed, pending a client meeting.** → Mitigation: build the webhook receiver per the spec's stated assumption, but do not mark `sybill-ingestion` complete or wire it into production until confirmed; the answer received so far ("there are considerations as well") suggests it may not be a simple binary choice.
- **[Risk] The Airtable staging-table schema is not yet designed**, only the field set going into it is known (the full standard fields of the in-scope HubSpot objects). → Mitigation: design the schema as part of this change's `airtable-staging` capability rather than waiting on further external input, since the data going in is already known.
- **[Risk] A single shared Postgres instance is a logical, software-enforced isolation boundary, not a physical one.** A coding mistake (a missing tenant-scope filter) could theoretically leak across tenants in a way dedicated-per-tenant infrastructure could not. → Mitigation: the `tenant-isolation` capability is a non-negotiable, zero-tolerance test gate, not a nice-to-have; every isolation test must pass at 100%, every time, and re-run on every future change, not just once at launch.
- **[Risk] HubSpot Developer test credentials and the Google Cloud OAuth client for FastMCP's OAuth Proxy are both still pending.** → **Partially resolved 2026-08-12: real HubSpot Public App and MCP Auth App credentials are registered, and both installs plus a real end-to-end CRM object pull are confirmed working against a real test portal** (see the Decisions above). The Google Cloud OAuth client for the live session remains the one still-pending credential; live end-to-end testing of that path still waits on it.

## Migration Plan

No existing production system to migrate from; this is new build-out on top of a cleaned repository. Rollout is incremental by capability: `hubspot-oauth` and `token-vault` first (nothing else functions without them), then `hubspot-data-pull`, then `airtable-staging` and `sybill-ingestion` in parallel (independent of each other), then `live-mcp-session` (depends only on `hubspot-data-pull` and `token-vault`, independent of the staging path), then `security-hardening` and `tenant-isolation` as a hardening and verification pass across everything built, including the live session. No rollback strategy beyond standard git revert is needed, since nothing is deployed to a live client yet; the first real client portal onboards only once `tenant-isolation`'s tests pass at 100%.
