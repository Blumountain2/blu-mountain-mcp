## What this project is

A multi-tenant HubSpot data sync service for Blu Mountain's Intelligence System. It authenticates to each client's HubSpot portal (one shared HubSpot Public App, OAuth v3 with PKCE, installed separately into each client), reads a defined set of read-only HubSpot data per client, and stages normalized, client-tagged copies of it into Airtable. It also ingests Sybill call transcripts via webhook and stages those the same way.

A scheduled batch job pulls HubSpot data per tenant and stages it into Airtable, which analysis jobs and dashboards read from. Separately, a live, interactive MCP session lets Blu Mountain staff connect through Claude Desktop, Claude Code, or Claude Cowork — identically from any of the three — authenticate via Google Workspace, and query one selected client's HubSpot data live. This is built with FastMCP's own OAuth Proxy wrapping a Google Workspace OAuth client, not WorkOS, WorkOS is no longer part of this project. A separate direct Google/Microsoft JWT verification path also exists (`gateway/session/staff_auth.py`), but is not wired into `main.py`: no planning document ever identified a consumer for it distinct from what the live session already does, so it's kept in the codebase, unhooked, in case a future non-MCP consumer (e.g. a web dashboard) needs it. See the implementation plan and design.md's decision log. Ask a teammate for the current phase plan and additional architecture detail if you need it.

## Current build state

HubSpot OAuth, the token vault, the data pull, Airtable staging, Sybill ingestion, and the live session are now all built, organized into `auth/`, `sync/`, `webhooks/`, and `session/` subpackages under `gateway/` (plus `main.py`, `config.py`, `db.py`, and `schema.sql` at the root). All 301 tests pass (`pytest tests/` inside the container, run against a real Postgres instance via `docker compose`), and `docker compose up` serves `/health`, `/`, and the live session's `/mcp` mount correctly, checked by actually sending requests, not just reading the code. `/staff/me` no longer exists: `session/staff_auth.py` is kept in the codebase but unhooked from `main.py`, see the Architecture section below.

**HubSpot access pivoted from MCP to plain REST** (`openspec/changes/hubspot-rest-api-pivot`, cutover completed 2026-09-02 — see the Data pull section below for the full architecture). The MCP Auth App (spec Section 4.1) and `mcp.hubspot.com` are gone entirely: no code, no config, no `mcp_tokens` table, and the app registration itself was deleted directly in HubSpot's developer account (not just token revocation). `HubSpotDataPullClient` now reads `api.hubapi.com` directly using the Public App's own vaulted token — the single `/install` step is the whole onboarding flow now, there's no second app to install. This is a deliberate, knowing reversal of the original spec's Section 1.3 (mcp.hubspot.com as the data-access mechanism), driven by three real findings from this session: the Public App's own token was never actually used for any live pull under the old design, REST has real documented equivalents for everything MCP provided (plus a strictly better authoritative `hubspotDefined` custom-field flag MCP never exposed), and `HubSpotDataPullClient`'s existing method-level abstraction boundary meant this was a contained rebuild of one module's internals, not a rewrite of the project.

The live session's FastMCP OAuth Proxy is verified end-to-end: a real Google Cloud OAuth client is registered, and a real Google login (Workspace domain `blumountain.me`) through MCP Inspector completed the full flow — Dynamic Client Registration, `/authorize`, Google consent, `/auth/callback`, token exchange, and a real authenticated MCP session. Airtable staging is likewise confirmed for real: a real staging base exists, its schema was provisioned via `ensure_schema()`, and a real pull-and-stage cycle succeeded against both test portals. The live session's tools were originally three (`list_my_tenants`/`select_tenant`/`query_hubspot_data`), confirmed for real through a real, authenticated MCP Inspector session — including `select_tenant`'s ambiguous-name-candidates behavior. **Since replaced** (`openspec/changes/separate-vertical-client-agents`, task 6): the single generic `query_hubspot_data` tool is retired, split into four category-scoped tools (`query_crm_records`, `query_engagement_records`, `query_marketing_content`, `query_users`), each accepting an optional `properties` parameter to narrow the response to specific fields — including custom ones. Confirmed live against both real test portals, including through a real `Client`↔`FastMCP` round trip with real (non-mocked) REST-based HubSpot pulls; full interactive MCP Inspector re-confirmation is still a human's manual step to run. Also separately covered by automated tests using the same real `Client`↔`FastMCP` in-memory round trip technique (`gateway/tests/session/test_live_session.py`, the `test_real_transport_*` tests), not just direct Python calls with monkeypatched auth. Check the actual module contents before assuming something is or isn't implemented — this file is a summary, not the source of truth.

Verified compatible for every API surface this project actually calls (`FastMCP`, `GoogleProvider`, `get_access_token`, `CallToolResult.data`/`.content`/`.is_error`, `Tool.name`) via direct signature inspection plus a real, non-mocked in-process `Client`↔`FastMCP` smoke test, and the full test suite passes against it. A real Google OAuth login through the live session (most recently a real reinstall on 2026-08-17, and the tenant-naming feature's live verification before that) has succeeded on this exact pairing, not just in this sandbox's own smoke test.

## Non-negotiables

These apply to every commit and every file in this repository.

- No celebratory or aspirational status claims. State only what was actually run and what actually passed.
- HubSpot access is read-only, absolutely. No write scopes, no write code paths, ever. Airtable is the only read-write integration in this system.
- Any multi-tenant code path needs an isolation test proving no cross-tenant data or error leakage before it's considered done.

## Architecture (target, per the implementation plan)

**Onboarding and token vault**:
- `/install` and `/callback` routes handle the OAuth v3 + PKCE flow for a client portal — the single, complete onboarding step (the MCP Auth App's second install step is gone, see the Data pull section below).
- Tokens are stored in Postgres, keyed by `hub_id` (portal-level authorization, not per-user), AES-256 encrypted with a per-tenant key derived from a single root key (`APP_ENCRYPTION_KEY`) via HKDF, using `hub_id` as derivation context. No tenant's key is ever derivable from another tenant's data.
- Tokens refresh proactively on a five-minute buffer, serialized per tenant via Postgres advisory locks so multiple instances never race to refresh the same tenant. `TokenVault` (`auth/token_vault.py`) stays parameterized by `table_name`/`refresh_fn` even though only one instance (`vault`, backed by `tokens`) exists today — real, testable flexibility kept from when a second instance (`mcp_vault`, backed by `mcp_tokens`) also existed, not speculative scaffolding.
- `/callback` renders a styled HTML page (`auth/pages.py`), not raw JSON — the actual caller is a portal admin's browser at the end of HubSpot's consent redirect, not a programmatic client. The success page confirms the single install is complete (no more "continue setup" link to a second step); error pages show a plain-language message and a retry link. Both derive the current URL from the incoming request's own host, so they're correct in any environment without code changes.
- HubSpot's OAuth scope model has two request parameters, not one, and this project uses both: `scope` (required — a portal lacking any of these fails the *entire* install) and `optional_scope` (`HUBSPOT_OPTIONAL_SCOPES`, `auth/hubspot_oauth.py`'s `install()` — a portal lacking one of these just has it silently omitted from the grant). Confirmed live this distinction is load-bearing, not cosmetic: `marketing.campaigns.read` (needs Marketing Hub Professional+) and three CRM-object scopes possibly needing elevated account permissions (`crm.objects.line_items.read`, `sales-email-read`, `crm.objects.users.read`) all live in `optional_scope` specifically because requesting them as required broke real installs on a portal that couldn't grant them. The corresponding capabilities (CAMPAIGN, LINE_ITEM, EMAIL CRM objects, the USER object type) degrade gracefully — `pull_failed` for that one object/capability, not a crash — on a portal that didn't get the scope. **A scope's requested/optional status must be declared identically in two places**: the Public App's own manifest (`hubspot-app/src/app/app-hsmeta.json`'s `requiredScopes`/`optionalScopes`, deployed via `hs project upload`) *and* `config.hubspot_scopes`/`hubspot_optional_scopes` (which query param `/install` sends it under) — HubSpot validates against the app's own registered declaration regardless of which param a request uses, so editing only one side silently doesn't fix anything (confirmed live the hard way: three separate failed reinstalls before this was understood).

**Data pull** (`openspec/changes/hubspot-rest-api-pivot`, cutover completed 2026-09-02 — REST-based, reads `api.hubapi.com` directly with the Public App's own vaulted token; the MCP-based design this replaced is gone, not just superseded in code — the MCP Auth App's registration was deleted directly in HubSpot):
- A per-tenant client (`sync/hubspot_client.py::HubSpotDataPullClient`) has no runtime tool-discovery step the way the MCP-based version needed — REST's endpoint set is fixed and documented ahead of time, so every endpoint this project calls is a hand-enumerated constant, reviewed once. Several real endpoint families, not one uniform dialect the way MCP's `query_crm_data` was, all confirmed live against both real test portals:
  1. **Core CRM objects** (contacts, companies, deals, tickets, line items, products, calls, emails, meetings, notes, tasks, users) via `GET /crm/v3/objects/{type}`, paginated (`paging.next.after`). `pull_crm_objects()` authors the request from `CRM_OBJECT_TYPES`/`CRM_OBJECT_REST_SLUGS`, never from caller input. An explicit `properties=` request **narrows** the response — confirmed live this is a real behavior change from the old MCP-based mechanism (which was additive to HubSpot's default set); a few object-identity fields (`hs_object_id`, `createdate`, `lastmodifieddate`) persist regardless of what's requested, so it's not a *literal* exactly-these-fields guarantee.
  2. **Custom property discovery** via `GET /crm/v3/properties/{type}` (`discover_object_properties()`/`discover_object_property_definitions()`) — returns every property for a type in one call, including an authoritative `hubspotDefined` boolean HubSpot's own API provides directly; the prior MCP-era `is_custom_property_name()` heuristic (a hand-curated standard-name list) is gone, replaced by this real flag everywhere custom/standard status is reported.
  3. **Four non-standard object families**, each its own adapter rather than the generic CRM-objects path: CAMPAIGN (`/marketing/v3/campaigns`, Marketing Hub Professional+ tier-gated — see below), LANDING_PAGE/BLOG_POST (HubSpot's CMS API), OBJECT_LIST (`POST /crm/v3/lists/search` — a real, read-only search despite the HTTP verb, this project's one deliberate exception to "GET only," reviewed and flagged explicitly).
  4. **Five generic capabilities** (`list_read_only_tools()`/`pull_object()`, a fixed hand-maintained set replacing MCP's dynamic tool discovery): `owners` (`/crm/v3/owners/`), `organization_details` (composed from `/settings/v3/users/teams` + `/settings/v3/users/` + `/account-info/v3/details` — the `/teams` sub-resource needs its own scope, `settings.users.teams.read`, distinct from the base `settings.users.read`, confirmed live the hard way), `content_analytics` (`/analytics/v2/reports/pages/total`), `marketing_email_analytics` (`/marketing/v3/emails/statistics/list`), `campaign_attribution` (aggregates per-campaign metrics — excluded from `pull_all()`'s own generic loop specifically to avoid pulling the same campaign metrics twice, since `pull_all()` already calls `pull_campaign_data()` directly for its own `campaign_data` key; still fully reachable as its own capability everywhere else).
  5. **Per-campaign metrics** via `pull_campaign_data()` — enumerates real campaign IDs first (`/marketing/v3/campaigns`), then calls `/marketing/v3/campaigns/{id}/reports/metrics` once per campaign, concurrently but bounded (`_MAX_CONCURRENT_CAMPAIGN_PULLS`).
  - Every method with an optional `client=` param also accepts `headers=` — a caller that already resolved this tenant's Authorization header (e.g. `pull_all()`, resolving it once for a whole multi-call pull) passes it straight through instead of a second vault fetch per call. Found and fixed during this pivot: the first version of this rewrite re-fetched the token on every single call even when a caller had already done so once.
  - **CAMPAIGN's account-tier gating** (Marketing Hub Professional+) is real and confirmed live to differ between the two test portals — `149094230` has it (real campaign data returned), `148997330` doesn't (`403`, caught and degraded to `pull_failed`, not a crash). `marketing.campaigns.read` is requested as an *optional* OAuth scope specifically because of this (see the Onboarding section above) — matches HubSpot's own tier gate instead of fighting it.
  - Two developer test portals exist for exercising this: `hub_id=148997330` (baseline) and `hub_id=149094230` (Enterprise/Marketing-Hub-Pro-equivalent tier, with a real campaign, for the account-tier-gated tools). Both are free — HubSpot's developer test accounts include a 90-day enterprise-feature trial by default and cannot be upgraded, so a fresh account is the way to test a different tier, not an upgrade.
  - **`QUOTE` added** (2026-09-02, cross-referencing Blu Mountain's own vertical framework documentation): two of six frameworks (Services/Project, Transactional) name Quotes as a secondary Opportunity/Proposal-stage signal. `crm.objects.quotes.read` requested as an optional scope, the same posture as `CAMPAIGN`.
  - **The client agent's own tool loop now actually reaches custom fields** (`frameworks/pull_agent.py`, 2026-09-02): its `pull_object_type` tool previously called `pull_crm_objects` with no `properties=`, so no custom property (health score, MRR, plan tier, delivery status, project fields — every vertical framework's Tier 2/3 metrics depend on one) ever reached a gathered record, even though the discovery mechanism existed. Fixed to call `discover_object_properties()` first and request every real, discovered property explicitly. Confirmed live against `148997330`: CONTACT went from HubSpot's ~6-property default set to the portal's full real property list (hundreds of fields, including custom ones like `jobtitle`). Surfaced and fixed a related latent bug in the same pass: `discover_object_property_definitions()`'s own token-fetch call wasn't inside its try/except, so a vault failure could propagate uncaught out of a method whose whole contract is "never crash, just degrade to `[]`."
  - **Custom object support** (`openspec/changes/custom-object-support`, 2026-09-03): `HubSpotDataPullClient` gained `discover_custom_object_schemas()`/`pull_custom_object()`/`discover_custom_object_properties()` — a portal's custom objects are discovered at runtime (there's no fixed lookup table for these the way `CRM_OBJECT_REST_SLUGS` is for standard types; a caller must discover a custom object's `objectTypeId` first via `GET /crm-object-schemas/v3/schemas`, then read it via the same `GET /crm/v3/objects/{objectTypeId}` shape every standard object already uses). Exposed via `gateway/debug_api.py`'s `/debug/hubspot/{hub_id}/custom-objects*` routes. **All three integration points this task's own tasks.md originally deferred are now done, each as its own separate decision, not bundled in this original change**: `BaseAgent`'s tool loop (`client-vertical-agent-classes`, 2026-09-04), `live_session.py`'s tool surface (`list_custom_objects`/`query_custom_object`, 2026-09-08), and `profiling.py`'s field profiling (`profile_tenant_fields(..., custom_object_type_ids=...)`, 2026-09-08 — see the Live interactive session and Analysis model templates sections above).
  - **Resolved 2026-09-03 — the real root cause of every optional-scope gap this session chased.** `LINE_ITEM`, `USER`, custom objects (`crm.schemas.custom.read`/`crm.objects.custom.read`), `QUOTE`, `sales-email-read` (EMAIL), and `crm.objects.products.read` all stayed ungranted through multiple correctly-timed reinstalls, which this file previously (and incorrectly) attributed to several different theories: a HubSpot "sensitive scopes" Ecosystem Quality review process, Enterprise-tier gating, the installing user's Super Admin status, and a dead scope name. **All of that was a red herring.** The actual cause: HubSpot portals have a separate **Connected Apps admin data-permissions toggle**, per optional scope, that a portal admin must explicitly enable before that scope is even selectable on the OAuth consent screen — shown there as a locked checkbox with "This permission is disabled for this app by an admin." Worse, the consent screen itself was serving a **stale/cached permission set** in a normal (non-incognito) browser tab even after the admin toggle was flipped. Once the user (a) enabled the scopes in the portal's Connected Apps admin settings and (b) reinstalled in a fresh incognito session, every one of the above scopes granted immediately on both portals, confirmed via token introspection (`GET /oauth/v1/access-tokens/{token}`). Only two optional scopes are still absent, and both are expected: `marketing.campaigns.read` on `148997330` (that portal genuinely lacks Marketing Hub Professional+, the real tier gate) and `e-commerce` (removed from the manifest in build #12 — no longer requested at all, superseded by `crm.objects.products.read` which now works on its own).
    - **Practical implication for any future scope addition**: after adding a new optional scope to the manifest and reinstalling, if it doesn't show as granted, check the portal's Connected Apps admin settings for a locked/disabled toggle on that scope *before* assuming a HubSpot-side review or tier gate — and always test with a fresh incognito session, not a reused browser tab, since the consent screen caches stale permission state.

- This pull capability is shared infrastructure: both the scheduled job and the live session use it identically, it doesn't decide who's allowed to call it.

**Live interactive session** (active, built with FastMCP's OAuth Proxy, not WorkOS):
- FastMCP's OAuth Proxy wraps one manually registered Google Workspace OAuth client, presenting a Protected Resource Metadata-serving, DCR-compliant interface to Claude Desktop/Cowork/Code, so the "Connect" experience works the same way it would for any other remote MCP server.
- It issues its own audience-scoped JWT to the connecting client rather than forwarding Google's token, this is what satisfies the no-token-passthrough requirement, Google's token never leaves the proxy.
- Enforces the Google Workspace domain allowlist on every login, rejecting sign-ins from outside it.
- Tenant access is default-open, not an allow-list: any staff member who signs in successfully has access to every installed tenant, unless a row in `staff_tenant_restrictions` explicitly restricts them from a specific one. A session with more than one permitted tenant must have exactly one selected before any data is returned. See design.md's decision log for why this replaced an earlier allow-list design.
- Every interactive access is audited by staff identity and tenant, this is the only record that can attribute a HubSpot read to a specific person, since HubSpot itself only sees the shared app credential.
- `main.py` compensates for discovery/challenge URLs that don't resolve correctly given the outer `/mcp` mount, in two different ways as of 2026-09-09. The RFC 8414 authorization-server metadata's standard discovery path is still a redirect. The RFC 9728 protected-resource metadata route is **not** a redirect anymore — it serves a corrected document directly, because FastMCP's own equivalent document (and its `WWW-Authenticate` challenge header) has a real trailing-slash bug in this exact `fastmcp==4.0.0b2` version (`AuthProvider._get_resource_url` always appends `/` when FastMCP's own internal mount path is `/`, which this outer-mount setup requires) — confirmed live against a real MCP Inspector "Add connector" attempt, which rejects the mismatch outright. A `_McpMountSlashCompatibility` ASGI middleware (registered globally via `app.add_middleware`, not scoped to the mount, since Starlette's `Mount` already strips the `/mcp` prefix before any per-mount wrapper would see the unstripped path) does two more things at the wire level for the same underlying bug: rewrites a bare `POST /mcp` so it's answered directly instead of 307-redirecting to `/mcp/` first, and corrects the same trailing slash in the `WWW-Authenticate` header's `resource_metadata` URL. See design.md's decision log for the full mechanism. All of the above confirmed fixed end to end against real MCP Inspector and Claude Code sessions — first independent of real Google credentials (this fix is at the discovery/mount layer, before any OAuth exchange happens), and since confirmed again as part of the full real-login flow now that those credentials exist (see above).
- Decided: Google only. Microsoft 365 OAuth Proxy parity was considered and explicitly not built for the live session; see design.md's decision log. This doesn't affect `staff_auth.py` below, which keeps its own separate Google/Microsoft support unchanged.
- **Custom-object tools added (2026-09-08)**: `list_custom_objects()`/`query_custom_object(object_type, properties=None)`, reachable from a live interactive session, closing a gap `custom-object-support`'s own tasks.md had explicitly deferred (it named `pull_agent.py`'s tool loop, `live_session.py`'s category tools, and `profiling.py`'s field profiling as separate integration decisions — all three are now done, see the note in the Data pull section above). Unlike `BaseAgent`'s tool pair and `debug_api.py`'s routes (which both require the exact `objectTypeId`), `query_custom_object` also resolves a friendly name or label ("transactions", "Transaction") against this tenant's own real, live schema data — there's no fixed alias table the way `resolve_object_type_aliases` has for standard CRM object types, since a custom object's very existence and naming is tenant-specific; an ambiguous name returns `{"ambiguous": True, "candidates": [...]}` rather than guessing, the same discipline `select_tenant` already uses. Found via real usage, not anticipated: the first version required the exact `objectTypeId` only, and a real MCP Inspector session immediately hit the friction of not being able to pass the name shown by `list_custom_objects`. Confirmed live against `149094230`'s real "Transaction" custom object (`objectTypeId 2-252820399`) through a real `Client`↔`FastMCP` round trip, resolving both by exact ID and by name. `gateway/scripts/live_verification.py`'s step 3 now exercises both paths, not just the four category tools.
- Beyond the six data tools above, the session also exposes two MCP prompts (`tenant_pipeline_overview`, `tenant_recent_activity`) — static instruction text guiding a connecting model through select_tenant + the right query_crm_records/query_engagement_records calls for a common ask (open pipeline, recent activity), not data access on their own. A deliberately small, first pair added 2026-08-19; real staff usage (none exists yet beyond Blu Mountain's own test portals) should drive what's added next, not a guess. `gateway/session/live_session.py`'s `@mcp.prompt`-decorated functions must return a bare `str`, not the `list[Message]`/`list[dict]` shape this pinned FastMCP version's own docstring example shows — confirmed live that a dict message raises `PromptError` at render time on this version.

**Direct Google/Microsoft JWT verification** (kept, unhooked, not currently wired to anything):
- `gateway/session/staff_auth.py` verifies an already-issued Google or Microsoft token directly, a plain API guard, not an MCP server. Enforces `GOOGLE_HOSTED_DOMAIN`.
- Built before the live session's FastMCP OAuth Proxy path was understood as buildable. No planning document ever identified a distinct consumer for it, so `main.py` no longer routes to it (`/staff/me` doesn't exist). Kept in the codebase in case a future non-MCP consumer (e.g. a web dashboard) needs a plain bearer-token verifier; import `session.staff_auth` directly if so. Do not wire it back into `main.py` without a concrete reason to.

**Staging**:
- Normalized HubSpot data and Sybill call transcripts are written into Airtable via `pyairtable`, every record tagged by client.
- The Sybill webhook receiver validates payload signatures (HMAC, Svix-style) and rejects stale or unsigned requests before staging.

**Analysis model templates** (new capability, `gateway/frameworks/`, layered on top of the pull/staging architecture above — see `openspec/changes/analysis-model-templates/`, Sections 1-3 built and confirmed live, Section 4 in progress, Sections 5-6 open/deferred):
- One shared, unmodified vertical framework (SaaS, PLG, Marketplace, E-commerce, Services/Project, Transactional — the six real verticals in Blu Mountain's delivered documentation, not "Advertising," which was only ever this project's own placeholder example), plus one vertical-agnostic operational skill and one runtime prompt, all Blu Mountain-authored and ingested verbatim. Corrected from an earlier draft that assumed a persisted, forked, per-tenant *copy*: the real delivered content (`Weekly_Diagnostic_Prompt.md`) is explicitly parameterized at runtime via `{CLIENT_NAME}`/`{VERTICAL_FRAMEWORK_NAME}` injection, not edited ahead of time — so this project stores and serves that content unmodified (`gateway/frameworks/store.py`, `analysis_content` table, append-only/versioned) and never authors or forks it.
- Tenant field profiling (`gateway/frameworks/profiling.py`) reuses the existing, already-allowlisted `pull_crm_objects()` — no new HubSpot access path — to determine which of a tenant's real fields are actually populated, cross-referenced against a known vertical's `trust_by_default`/`unreliable_by_default` guidance (`gateway/frameworks/guidance.py::FRAMEWORK_PROPERTY_GUIDANCE`, hand-verified against the real source text for all 6 verticals). Confirmed live against `149094230`'s real "Transaction" object: `status`/`transaction_date` surfaced as real `needs_review` candidates.
- **The persisted tenant onboarding profile is retired (2026-09-08).** `gateway/frameworks/onboarding.py`, `tenant_onboarding_profiles`/`tenant_onboarding_profile_fields`, and the `tenants.vertical` column (plus `frameworks/vertical.py`'s `get_tenant_vertical`/`set_tenant_vertical`/`resolve_vertical_or_raise`) are all gone — dropped/deleted outright, the same "codebase, not Postgres rows" direction `client-vertical-agent-classes` already took for agent configuration, applied here once a real-caller audit confirmed nothing in production still called any of it after that migration. In its place: `gateway/scripts/generate_confirmed_fields.py` calls `profile_tenant_fields` directly (a client's vertical now comes from its registered agent class, not a database column) and prints a proposed `CONFIRMED_FIELDS` dict — split into framework-trusted (safe to auto-propose), framework-flagged-unreliable (deliberately excluded), and needs-a-human-decision — for a person to review and paste into that client's file. No persistence layer in between; the decision lives in git, once made, the same way every other per-client decision in `gateway/frameworks/agents/clients/` does. **`openspec/specs/tenant-template-instantiation/` (the canonical capability spec for the removed onboarding-profile-production system) was deleted directly, 2026-09-10** — not through the archive tool, the same pragmatic precedent already set for `vertical-agent-templates`/`client-agent-instantiation` (see `client-vertical-agent-classes` above): a capability spec can't be rebuilt down to zero requirements by that tool, and there was no code behind the correction either way. `tenant-field-profiling` (the underlying field-profiling capability, still very much alive) and `analysis-template-schema`/`vertical-pull-agent`/`hubspot-query-tool-surface` (which each had one stale requirement mentioning "onboarding profile" as a still-existing artifact) were corrected in place instead, since those capabilities themselves are still real.
- Both real test portals were profiled again 2026-09-08 via the new generator: `148997330`'s (SaaS) and `149094230`'s (Marketplace) framework-trusted fields turned out to be almost entirely HubSpot metadata (`hs_object_source`, timestamps), not business signals like `health_score`/`plan_tier`/`jobtitle`/`take_rate` — those remain `needs_review`, deliberately not auto-populated into `CONFIRMED_FIELDS`, since doing so would have narrowed each client's agent away from full field discovery for comparatively little gain. Both clients' `CONFIRMED_FIELDS` stay empty for now, pending an actual human curation pass.
- This capability does not build the downstream analysis jobs (Funnel, Maintenance, KPIs & Reporting) that would actually consume a stored framework plus a tenant's onboarding profile against staged Airtable data — deliberately deferred as a separate, later change (`tasks.md` Section 6), and it's still an open question whether those jobs live in this repo at all (see design.md's Open Questions).
- All HubSpot access here is read-only, same as everywhere else in this project: profiling only ever reads via the existing allowlisted pull path, never writes.

**Vertical/client agent separation — now real, separate code, not database rows** (`openspec/changes/client-vertical-agent-classes/`, built and confirmed live 2026-09-04 — a further, deliberate reversal beyond `openspec/changes/separate-vertical-client-agents/`'s already-deliberate reversal of `analysis-model-templates/design.md`'s Non-Negotiable #6; see that change's `design.md` "Context" for the full three-round history of this recurring decision). `vertical_agent_templates`/`client_agent_instances` and `gateway/frameworks/vertical_templates.py`/`client_agent.py` are gone — dropped and deleted outright, not deprecated in place:
- **Class hierarchy, replacing the two-tier database model.** `gateway/frameworks/agents/base.py::BaseAgent` holds the tool-calling loop mechanics (the bounded while-loop, tool dispatch, `MAX_TOOL_CALLS` safety cap, hub_id-scoped `HubSpotDataPullClient` construction, audit logging) — identical for everyone because the Anthropic tool-use API shape forces it, not a business decision. `gateway/frameworks/agents/verticals/*.py` — one subclass per vertical, setting `VERTICAL`/`SYSTEM_PROMPT_ADDITIONS` as real class attributes. `gateway/frameworks/agents/clients/*.py` — one subclass per client, setting `HUB_ID`/`CONFIRMED_FIELDS` (which standard-object or custom-object fields this client's agent looks at — narrows the tool's HubSpot request when set, falls back to full live discovery per object type when not). `gateway/frameworks/agents/registry.py` — a self-registering `@register_client_agent(hub_id)` decorator, not one hand-maintained dict (a merge-conflict hotspot at the ~50+ clients this project expects); an unregistered `hub_id` raises a clear error rather than falling back to a generic agent. `gateway/frameworks/pull_agent.py::run_client_agent(hub_id)` is now a thin wrapper: registry lookup, instantiate, `.run()` — kept only because it's still the real call site every other module imports; `vertical`/`allow_unqualified` parameters were dropped entirely rather than kept as no-ops, since no real caller ever passed them.
- **Still one shared Anthropic API credential, still one shared deployment** — this reversal is entirely about application code structure, not infrastructure duplication. No machine-learning training or fine-tuning anywhere, unchanged from before.
- **Custom-object reach, built directly into `BaseAgent` this time** (`list_custom_objects`/`pull_custom_object` tools, wired to `custom-object-support`'s existing `discover_custom_object_schemas()`/`pull_custom_object()`/`discover_custom_object_properties()`) — the integration point that change's own tasks.md explicitly deferred. Confirmed live 2026-09-04 against `149094230`'s real "Transaction" custom object (`objectTypeId 2-252820399`) two ways: through the agent's own autonomous run (the model organically chose to call these tools mid-run, unprompted, and gathered 3 real records) and through a direct executor-dispatch check independent of the model's own judgment.
- **Custom HubSpot field access** (`sync/hubspot_client.py`): `HubSpotDataPullClient.discover_object_properties()`/`discover_object_property_definitions()` + `pull_crm_objects(..., properties=...)` reach any named property. `properties=` narrows the response (REST pivot behavior); HubSpot's own `hubspotDefined` flag (from `GET /crm/v3/properties/{type}`) is the authoritative custom/standard signal — see the Data pull section above.
- **The live session's HubSpot query surface** (`gateway/session/live_session.py`) is unaffected by this change — still the four category-scoped tools (`query_crm_records`, `query_engagement_records`, `query_marketing_content`, `query_users`) as of this migration, unrelated to the vertical/client agent's own separate tool surface. (Two more tools, `list_custom_objects`/`query_custom_object`, were added to it 2026-09-08 — see the Live interactive session section above; still a separate tool surface from the vertical/client agent's own.)
- Confirmed live 2026-09-04 (`gateway/scripts/live_verification.py`, rewritten for the class-based path): all 6 vertical classes present, both real clients (`148997330` → `SaaSAgent` subclass, `149094230` → `MarketplaceAgent` subclass — corrected from a wrong historical `saas` assignment on `149094230`, whose real vertical is marketplace) registered and running real agent loops against real HubSpot + real Anthropic, gathering 21 real records each.
- **What was deliberately not carried over, because there was nothing real to carry**: both real `client_agent_instances` rows had zero confirmed-relevant fields and all 6 `vertical_agent_templates` rows had empty `system_prompt_additions` at the time of this migration — checked directly against the live database before migrating, not assumed. Both real clients start with `CONFIRMED_FIELDS = {}` (full discovery, same as before), with the prior `needs_review` field names left as a code comment for a human to actually curate.
- **A client's agent cannot override its vertical's behavioral instructions, only add fields/objects** — resolved directly by the user during scoping: verticals decide *how to think*, clients only supply *what's true about them*, matching the database model's own original boundary (`vertical_agent_templates.system_prompt_additions` vs. `client_agent_instances.injected_documentation`). Not a permanent constraint — adding an optional per-client override later, if a real client ever needs one, is a small additive change to `BaseAgent`, deferred until then rather than built speculatively now.
- Operator runbooks: `context/VERTICAL_AGENT_CLASSES.md` (create/edit/save a vertical), `context/CLIENT_AGENT_CLASSES.md` (create/edit/save a client, including setting `CONFIRMED_FIELDS`). Both state plainly that there is no admin UI — "saving" means a commit and a deploy.

**Security controls**:
- Per-tenant rate limiting via a Postgres token-bucket table, no Redis.
- Per-tenant audit log in Postgres: every pull, who, what, when, which client, minimum 60 day retention.
- No credentials in logs, prompts, or tool descriptions, ever.

## Development commands

```bash
# Copy the environment template and fill in real values
cp .env.example .env

# Generate the app-level token encryption key
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

# Start the stack (Postgres + the service)
docker-compose up -d

# Check service health
curl http://localhost:8888/health

# Local development without Docker (requires Python 3.11+ to match the container)
cd gateway && pip install -r requirements.txt

# Run the full test suite (rebuild first if source changed since the last image build)
docker compose build mcp-gateway
docker compose run --rm --user 0 mcp-gateway sh -c "pip install --no-cache-dir -q -r requirements-dev.txt && pytest -q"

# Single entry point: builds the image, runs the full test suite, then smoke-tests
# the real running container over real HTTP. No external credentials needed — this
# is also what .github/workflows/ci.yml runs on every push/PR to dev/main.
python3 scripts/test_all.py

# Non-mocked verification against real Postgres/HubSpot/Anthropic (needs real
# vaulted test-portal tokens and a real ANTHROPIC_API_KEY already configured for
# the dev stack — not for CI, for confirming against reality on demand)
docker compose up -d
docker cp gateway/scripts/live_verification.py mcp-gateway:/app/live_verification.py
docker exec -w /app mcp-gateway python3 live_verification.py

# MCP Inspector, for poking at the live session's /mcp endpoint directly (Node >=22.19 required)
npm install
npm run inspector          # web UI: connects to http://localhost:8888/mcp over Streamable HTTP
npm run inspector:cli      # headless: lists tools via tools/list, no browser

# Postman collection for this service's own exposed HTTP endpoints (not HubSpot's
# API, and not the /mcp mount — that's MCP Inspector's job, see above). Import
# postman/blu-mountain-mcp.postman_collection.json, set its sybill_webhook_secret/
# hubspot_app_client_secret collection variables to match the running server's own
# .env, and run it — the two webhook requests carry a pre-request script that
# computes a real, valid signature, confirmed live via `npx newman run
# postman/blu-mountain-mcp.postman_collection.json --env-var sybill_webhook_secret=...
# --env-var hubspot_app_client_secret=...`. The uninstall-webhook request is
# genuinely destructive against whatever hub_id it targets (test_hub_id) — point it
# at a disposable test tenant, never a real client's.
```

The test suite runs against its own `mcp_test` Postgres database, never the same `mcp` database `docker compose up`'s dev stack uses — `gateway/tests/conftest.py`'s `_pool` fixture truncates every table it touches after each test, and running it against `mcp` directly destroyed a real, verified tenant install twice in one session before this was fixed. `mcp_test` is created automatically on first run (via a maintenance connection to Postgres's own `postgres` database), nothing to set up by hand.

The test command's `--no-cache-dir` isn't optional cleanup: `--user 0` is there because `/opt/venv` is root-owned from the build stage and installing `requirements-dev.txt` into it needs that privilege, but the Dockerfile's `HOME=/app` stays set regardless of `--user`, and `/app` itself is owned by the non-root `mcpgateway` user — so pip's default cache dir (`$HOME/.cache/pip`) is unwritable by root here specifically, and warns instead of failing. Skipping the cache avoids that mismatch entirely.

**MCP Inspector** (`package.json` at repo root, dev-only Node tooling — no production code lives there): `@modelcontextprotocol/inspector@^2.2.0`, the version aligned with the 2026-07-28 MCP protocol revision `fastmcp`/`mcp` were upgraded to below. Requires Node >=22.19 (an older Node still runs it, just with an `EBADENGINE` warning). `npm run inspector` needs `docker compose up`'s stack already running, since it connects to the live session's real `/mcp` mount — its OAuth flow is confirmed working end to end against the real Google Cloud OAuth client (see above). Launch it with no `--transport`/`--server-url` flags and add the server through the UI itself — passing those flags on the command line puts Inspector in a read-only "ad-hoc server" mode with no way to trigger the OAuth login.

## Configuration

Environment variables are defined in `.env.example`. Key groups:
- HubSpot Public App OAuth (Flow B, the only HubSpot install flow — see the Onboarding and Data pull sections above for why): `HUBSPOT_APP_CLIENT_ID`, `HUBSPOT_APP_CLIENT_SECRET`, `HUBSPOT_REDIRECT_URI`, `HUBSPOT_SCOPES` (required scopes — a portal lacking any of these fails the whole install), `HUBSPOT_OPTIONAL_SCOPES` (a portal lacking one of these just doesn't get it granted; must match `hubspot-app/src/app/app-hsmeta.json`'s own `optionalScopes` declaration, not just this env var — see the Onboarding section above)
- `OAUTH_STATE_TTL_MINUTES` (default 10): the in-flight PKCE state validity window for `/install` -> `/callback`
- Postgres: `DATABASE_URL` and its component parts
- Token encryption: `APP_ENCRYPTION_KEY`
- Airtable: `AIRTABLE_SERVICE_ACCOUNT`, `AIRTABLE_API_KEY`, `AIRTABLE_BASE_ID`
- Sybill: `SYBILL_WEBHOOK`
- Debug HubSpot data API (`gateway/debug_api.py`, `/debug/hubspot/*` — a plain HTTP surface for pulling a real installed tenant's HubSpot data via Postman rather than the MCP protocol, since Postman can't represent MCP naturally): `DEBUG_API_KEY` — empty by default, which makes every request 401 unconditionally (fail-closed). Every successful pull is recorded in `audit_log`, same as any other HubSpot access path. See `postman/blu-mountain-mcp.postman_collection.json`'s "Debug: HubSpot Data" folder.
- Direct Google/Microsoft (separate surface, `session/staff_auth.py`, kept but unhooked from `main.py`): needs `GOOGLE_CLIENT_ID`, `GOOGLE_HOSTED_DOMAIN`, `MICROSOFT_CLIENT_ID`, `MICROSOFT_TENANT_ID` — no client secret for either provider, this path only verifies already-issued JWTs (audience + provider JWKS), it never exchanges a code. **Now read via `config.settings`, like every other module** (corrected from an earlier `os.getenv` inconsistency — `config.py` already declared these fields, they just weren't wired up; `microsoft_tenant_id` defaults to `"common"`, Microsoft's own multi-tenant discovery alias, matching this module's original fallback exactly). **Deliberately absent from `.env.example` and `docker-compose.yml`'s `environment:` block** as of 2026-08-19, since nothing running today reads them and their presence there only produced an unset-variable warning on every `docker compose` invocation; add them back to both if `staff_auth.py` is ever wired back in.

FastMCP OAuth Proxy variables (`FASTMCP_GOOGLE_CLIENT_ID`, `FASTMCP_GOOGLE_CLIENT_SECRET`, `FASTMCP_BASE_URL`, `FASTMCP_OAUTH_REDIRECT_URI`, `FASTMCP_ALLOWED_GOOGLE_DOMAINS`, `FASTMCP_ACCESS_TOKEN_TTL_MINUTES`) are in `.env.example`, and the real Google Cloud OAuth client they hold values for is registered and confirmed working end to end (see the Current build state section above). `FASTMCP_OAUTH_REDIRECT_URI` is documentation-only (what to register on the Google Cloud OAuth client itself — `GoogleProvider` derives the real redirect path from `FASTMCP_BASE_URL`, it takes no separate full-URI parameter). `FASTMCP_ACCESS_TOKEN_TTL_MINUTES` **is now actually wired in** (`session/live_session.py::_build_auth`, `fastmcp_access_token_expiry_seconds=settings.fastmcp_access_token_ttl_minutes * 60`) — found and fixed during a codebase-wide config audit: it had been documented since before that audit but never passed to `GoogleProvider`, so FastMCP's own default expiry was silently governing every issued session token instead. WorkOS has been fully removed — no `WORKOS_*` variables remain anywhere in this project.
